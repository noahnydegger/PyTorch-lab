# PyTorch Lab learning guide

## Goal and current stage

Help the learner progress from basic PyTorch familiarity to explaining, running, and eventually extending DROP in the sibling repository `../drop-ch`. Assume basic Python and tensor familiarity. Introduce supervised learning, differentiation, neural networks, and hydrological modelling vocabulary as they become relevant.

The learner approved the sequence and asked to start with `01_tensor_shapes.ipynb`. Use their feedback on each lesson to decide where later notebooks need more depth or can move faster. Keep the lab environment separate from DROP's environment.

## How to build each lesson

- Use numbered notebooks as the main teaching format. Put reusable components in Python modules that the notebook imports. Create a module when it has a clear role in the eventual model, data pipeline, or training workflow. Reuse earlier code and show which file owns each responsibility.
- Start with a hydrological question and explain the data, units, inputs, target, and assumptions. Explain the maths with one calculation the learner can do by hand before introducing its PyTorch equivalent.
- For each new operation, explain in plain language what it does and show the before and after shapes with axis meanings. Start with explicit small shapes such as `(2, 3)` for two days and three stations. Explain how later models organise batch, time, and features, and verify the axis order when reading DROP.
- Interleave explanations and short tasks throughout the notebook. Define ML terms in plain language where they first appear. Give each task a collapsible solution that starts closed and ask the learner to explain one result.
- Use small CPU examples with repeatable inputs. Label synthetic examples clearly. When switching to observations, document the loader, time resolution, units, and missing values. Use the floodwater-harvesting project's existing loader for its processed discharge observations once its location and API are confirmed. Inspect the loader output before writing conversion code. If only discharge is available, use it for hydrographs, event analysis, and discharge-only baselines. Rainfall–runoff exercises require aligned meteorological inputs.
- Run notebooks from a fresh kernel and check companion scripts once dependencies are available. Use plots where they help explain a time series, model error, or routing response.

## Proposed sequence

| Lesson | Background and worked example | Hands-on exercise and checkpoint |
| --- | --- | --- |
| 01 · Tensors and hydrographs | Explain tensors, dtype, indexing, slicing, reshaping, reductions, broadcasting, and masks using a small table of daily discharge. Read a hydrograph and distinguish discharge from volume. | Select a gauge, mask missing readings, and compute volume above a threshold using the time step in seconds. Explain what happens to each axis and check one result by hand. |
| 02 · Supervised ML and baselines | Define features, targets, training, validation, generalisation, and leakage. Compare a persistence forecast with a linear model on lagged discharge. Introduce chronological splits and contrast them with holding out a catchment when the question is spatial transfer. | Build lag–target pairs, check the dates of a few pairs, and compare both baselines on the same held-out period. Explain why predicting tomorrow's discharge must use only information available today. |
| 03 · Autograd and linear regression | Work through prediction, residual, mean squared error, derivative, and one gradient-descent step with scalar examples. Repeat with tensors, then use `nn.Linear` and an optimiser. Explain gradient accumulation and why gradients are cleared each step. | Fit a small rainfall–runoff regression, predict the direction of one weight update, and verify it against the computed gradient. Relate the sequence of operations to a training loop. |
| 04 · Feed-forward neural networks | Explain layers, weights, biases, activation functions, and why stacked linear layers need a nonlinearity. Introduce `nn.Module`, batches, training-only normalisation, and evaluation mode. | Add a hidden layer to a model using recent rainfall and a catchment attribute. Compare it with linear regression on identical splits. Look at when errors occur on the hydrograph, including peaks and recessions. |
| 05 · Sequence data and vanilla RNNs | Build a `Dataset` and batch windows with a `DataLoader`. Explain hidden state, shared weights across time, and backpropagation through time. Connect recurrence to antecedent rainfall and show how earlier inputs can be hard to learn from. | Step through a tiny RNN by hand, then use `nn.RNN`. Verify the input, output, and hidden-state shapes. Compare short and long windows on the same data and check the split boundary. |
| 06 · LSTMs for runoff generation | Trace the forget, input, and output gates and the candidate update for one time step. Explain hidden versus cell state, static versus dynamic inputs, and sequence-to-one versus sequence-to-sequence outputs. An LSTM state is a learned quantity. Physical storage in a routing model has explicit units and a water balance. | Compare an RNN and LSTM on a controlled storm-response task. Inspect the output sequence and both final states. Add a static catchment attribute and explain how it becomes available at each time step. |
| 07 · River routing and mass balance | Distinguish local runoff from routed streamflow. Introduce hydrological response units (HRUs), directed river-network connectivity, travel time, area-based unit conversion, and the difference between discharge and water volume. | Route a pulse through two connected reaches. Compare instantaneous accumulation with delayed transport. Check inflow against outflow plus water still in transit over the chosen time steps. |
| 08 · Read and run DROP | Trace one batch through the actual data module, runoff prediction, routing, and observation comparison. Map the lab training loop to Lightning hooks. Interpret a hydrograph and introduce the project metrics from their code. | Run a small existing test or supported example, then explain a model output from data source to units, tensor shape, and metric. Reproduce one selected result using the repository's documented workflow once the environment and inputs are verified. |

## How the lab grows toward DROP

- In lesson 03, introduce the model and step functions in `pytorch_lab/nn/runoff_regression.py` and `pytorch_lab/training.py`. Trace the corresponding hooks in DROP's `RunoffNet`.
- In lesson 04, swap in a feed-forward model while reusing the training and evaluation steps. Show the import and call path from the notebook to the layer.
- In lesson 05, introduce a reusable time-window dataset and batch interface. Trace their counterparts in DROP's data module and identify how examples differ from HRU and graph batches.
- By the end of lesson 06, assemble a small runoff model from data, an LSTM layer, a prediction head, and step functions. Add a guided file trace through DROP's data module, `RunoffNet`, `nn/layers/lstm.py`, and the `DROP` entry class. Identify where routing enters and what additional data it needs. Use lessons 07 and 08 to work through routing internals and run the original project.
- Use concrete values, shapes, and a call trace whenever connecting a lab component to DROP. Distinguish a shared responsibility from a difference in how the framework manages it.

## DROP code-reading and execution milestones

1. Start with `../drop-ch/README.md`, `../drop-ch/AGENTS.md`, and `../drop-ch/pyproject.toml`. The checked-in Pixi project targets `linux-64`. Check the execution environment before choosing a workflow. The local `drop_ch_data` directory lists a harmonized Zarr store and model files or directories. Verify their contents and configured paths before relying on them.
2. Trace data through `project/data/datamodule.py`, including `HRUData` and `GraphDataModule`. Identify dynamic forcings, static attributes, observation targets, masks, time and spatial splits, and graph metadata. Follow the runoff step through `project/nn/runoff_net.py`, `project/nn/models/runoff_model.py`, and `project/nn/layers/lstm.py`. Explain which targets are used when pretraining the runoff model and when training the coupled model.
3. Trace `DROP` in `project/nn/drop_model.py` through unit conversion, instantaneous and coupled prediction paths, and `predict_step`. Follow routing into `project/nn/models/routing_model.py` and `project/nn/layers/transport.py`. Use `tests/test_drop_model.py` and `tests/test_routing.py` as executable examples of expected behaviour.
4. Start execution with focused CPU tests in a compatible environment. Then use the documented trained-checkpoint workflow or the fast development configuration as appropriate. Verify dataset paths, checkpoint compatibility, output location, and prerequisites. For a routed training run, check the PREVAH pretraining dependency described in the README. Record the configuration used and inspect the resulting shapes, units, and hydrograph.
5. Once the learner can explain and reproduce the original flow, discuss a single extension. A possible first design exercise is a diversion and storage element on a two-reach example. Define capacity, release, and water-balance checks before proposing changes to DROP. Agree on the extension before implementation.
